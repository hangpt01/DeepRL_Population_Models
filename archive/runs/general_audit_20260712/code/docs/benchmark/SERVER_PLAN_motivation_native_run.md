## 1. Headline: this is a CPU-only run. The GPU is unusable, and asking for it would only cost us time.

The instinct to "use both GPU and CPU" does not survive contact with the code. `backend.py` declares exactly which workloads have a CuPy kernel:

```
GPU_SUPPORTED_WORKLOADS = {"mechanistic_transition", "method:plus", "oracle_ablation:plus"}
```

Checked against the five methods this experiment actually runs ([backend.py:136-146](../../src/real_ecology_benchmark/backend.py#L136-L146)):

| Method | Side | `_cupy_scope_for_workload` | GPU? |
|---|---|---|---|
| `refplan` | general | `None` | **no** |
| `bamcts` | general | `None` | **no** |
| `ogsrl` | general | `None` | **no** |
| `plus_native` | ecological | `None` | **no** |
| `moor_native` | ecological | `None` | **no** |

The one GPU-accelerated path (`method:plus` → `plus_mechanistic_transition`) belongs to the **adapted** PLUS, which handoff §3 explicitly excludes from this run. `plus_native` is a different method name and is not in `PLUS_GPU_WORKLOADS`.

So a `--backend cupy` request would raise `BackendUnavailable` under strict mode, and a non-strict request would silently fall back to NumPy while still holding a GPU allocation. **Requesting GPUs would park the whole sweep behind the GPU fair-share queue for exactly zero speedup** — which is the stall that cost us the stress-116 run. Everything below is `--backend numpy` on the `comp` partition.

This is not a limitation in practice: the sweep is CPU-cheap (§4), and CPU is where our quota is largest.

## 3. The run grid

Generated by `scripts/make_motivation_native_manifest.py` → **1440 rows**:

- **2** reward modes (`safe` with P=5, `yield` with P=0 — a separate agent per mode)
- **9** populations (7 recoverable + 2 demographic sinks, reported separately)
- **4** dynamics families (ricker / allee / theta / regime)
- **4** observation noise levels (σ ∈ {0, 0.1, 0.2, 0.4})
- **5** methods with fixed filter routing:
  - `refplan`, `bamcts`, `ogsrl` → `filter=learned`
  - `plus_native`, `moor_native` → `filter=native_discrete`

`2 × 9 × 4 × 4 = 288` **cells**, `× 5` methods = 1440 rows. One offline dataset per cell, shared by all 5 methods in it (this is the §7.3 "same dataset" guarantee; `dataset_sha256` is logged per row).

**Plus a resolution replicate** (required by acceptance §7.6, "coarse vs fine does not flip the headline"): the two native methods re-run at a coarse and a fine grid. `288 cells × 2 natives × 2 grids = 1152 rows`, but these are the cheapest rows in the run (§4) and reuse the already-generated datasets.

### Manifest ordering is load-bearing
The manifest is **method-innermost** — the 5 rows of a cell are contiguous (verified: rows 0–4 are all `Egyptian vulture/ricker/σ=0.0/safe`). Choosing a block size that is a **multiple of 5** therefore keeps every cell's rows inside a single array task, so each cell's dataset is generated exactly once, by one task, with **no cross-task contention on the `ensure_dataset` lock**. This is free and it matters: 250 tasks racing on the same `public.npz` lock is a real failure mode.

## 4. Cost model (**measured**, full eval protocol: 5 seeds × 4 episodes × horizon 50)

Per-row wall time on one CPU core, on the real config (`configs/motivation_native.yaml`, `native_state_bins=61`, 4000-transition dataset). Measured on a login node under load, so these are **upper bounds**; a dedicated core will be faster.

| Row | Measured | Share of a cell |
|---|---|---|
| dataset generation (per **cell**, not per row) | **0.6 s** | ~0% |
| `plus_native` (native_discrete) | **4 s** | 0.4% |
| `moor_native` (native_discrete) | **8 s** | 0.9% |
| `refplan` (learned) | **53 s** | 5.8% |
| `bamcts` (learned) | **254 s** | 27.7% |
| `ogsrl` (learned) | **596 s** | **65.1%** |
| *(reference: adapted `plus`+ricker)* | *(104 s)* | *excluded from this run* |

**Per cell** = 0.6 + 53 + 254 + 596 + 4 + 8 ≈ **916 s (~15.3 min)**.
**Main grid** = 288 cells × 916 s ≈ **73 CPU-hours**.
**Resolution replicate** = 576 native rows × 2 grids, datasets already cached ≈ **1–2 CPU-hours** (the fine `b91` grid costs roughly 2× `b61` because value iteration scales with the square of the bin count).
**Total ≈ 75 CPU-hours.**

At `BS=5` (one cell per array task) and 240 concurrent cores: **288 tasks × ~15 min in two waves ≈ 35 min of compute.** A 4-hour per-task walltime gives ~16× margin on the slowest cell.

> **Sizing verdict: the 12–16 h budget is not the constraint — queue wait is.** The three general methods are 98.6% of the cost and **OGSRL alone is 65%**; the native baselines this whole build was about are ~1%. There is nothing to gain from a GPU (§1) and nothing to gain from a bigger CPU ask than the 250-core quota already allows.

**Do NOT spend the headroom on more seeds or longer horizons.** The eval protocol (5 seeds × 4 episodes × horizon 50) is locked by handoff §5 for comparability with the prior audited run. Changing it would silently break every cross-run comparison in the paper. The headroom is spent on the resolution replicate and a generous walltime, nothing else.

## 5. Slurm structure — reuse the P_safe pattern, which is proven here

Directory: `real_ecology_runs/motivation_native_20260711/`

```
motivation_native_20260711/

  manifests/            # manifest.csv (1440) + resolution manifests, sharded
  outputs/              # datasets/, private/, evaluation/, resolution/
  logs/                 # %x_%A_%a.out|err
  _canaries/
  run_block.sh          # one array task = BS contiguous manifest rows
  submit_blocks.sh      # block-packed submission, stays under MaxSubmit=1000
  run_analysis.sh       # cross-filter aggregation (afterany dependency)
  README.md
```

### 5a. Freeze the snapshot first
Per the P_safe lesson (and the audit's correction): snapshot **more than `src/`** — a spooled Slurm script must not read a tree that is being edited underneath it.

Snapshot: `src/real_ecology_benchmark/`, `configs/`, the `scripts/` used by the manifest/row/aggregation path, `real_ecology_data/`, and the docs + manifests for the run.

Jobs then `export ROOT=$RUN/code` and `cd "$ROOT"` — **never** the live repo.

### 5b. Packing (the `MaxSubmit=1000` constraint)
`BS = 5` → 288 array tasks (one cell per task, dataset built once, zero lock contention).
`BS = 10` → 144 tasks (two cells per task) if we want fewer tasks in flight.

Either is far under the 1000-task submit cap. **`BS=5` is the recommendation**: it aligns exactly with the cell boundary.

Concurrency: `--array=0-287%240` (240 concurrent tasks × 1 cpu = 240 CPUs, just under the 250 cap, leaving room for the analysis job).

### 5c. Per-task resources
```
#SBATCH --partition=comp
#SBATCH --time=04:00:00      # generous: a cell measures at minutes, not hours
#SBATCH --cpus-per-task=1
#SBATCH --mem=8G
```
`OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 MKL_NUM_THREADS=1` — NumPy must not oversubscribe; one row = one core is the accounting the 250-CPU cap assumes.

### 5d. Canary before the fleet — **array index 32, not 0**
The canary cell is Amur tiger / ricker / σ=0 / safe (the "assumption is correct" cell, where a native failure can only be an implementation bug). In the generated manifest that is **rows 160–164**, so at `BS=5` it is **array task 32**. Array task 0 is *Egyptian vulture* — the demographic sink, which is the worst possible canary because its behaviour is legitimately strange.

Verified row layout:
```
160 safe Amur tiger ricker sigma=0.0 refplan      learned
161 safe Amur tiger ricker sigma=0.0 bamcts       learned
162 safe Amur tiger ricker sigma=0.0 ogsrl        learned
163 safe Amur tiger ricker sigma=0.0 plus_native  native_discrete
164 safe Amur tiger ricker sigma=0.0 moor_native  native_discrete
```

Submit task 32 alone, confirm 5 `summary.json` files with `fallback_count == 0`, a single shared `dataset_sha256`, and non-degenerate action histograms; only then release the remaining 287. This is the step that caught the `ROOT`-not-exported bug on the P_safe run.

### 5e. The resolution replicate needs its own configs
`scripts/run_real_manifest_row.py` has **no way to vary `native_state_bins`** — the manifest has no such column and the runner would ignore it. The replicate is therefore driven by two dedicated configs, identical to `motivation_native.yaml` except for the grid:

- `configs/motivation_native_b31.yaml` (coarse)
- `configs/motivation_native_b91.yaml` (fine)

run against a **natives-only manifest** (`--natives-only`, 576 rows), into **separate output roots** (`outputs/res_b31`, `outputs/res_b91`) so they cannot clobber the main grid's native rows. The general methods do not depend on `native_state_bins`, so re-running them would burn ~99% of the cost for nothing.

## 7. Guardrails (each one is a bug we have already hit)

- **Never request a GPU.** Zero speedup, and it queues behind fair-share (§1).
- **`MaxSubmit=1000`** → pack rows; one job per row would be rejected at 1440.
- **`export ROOT=$SNAP`** and `cd "$ROOT"` in the spooled script — do not let jobs read the live tree.
- **`BS` must be a multiple of 5** so a cell's rows share a task and its dataset lock.
- **Aggregate with the cross-filter arguments**, or the headline table comes out empty and silent.
- **`collapse_penalty: 5.0` must be set explicitly** — the code default is 10.0, and `configs/motivation_native.yaml` is the only place P=5 is pinned. (`yield` mode forces P=0 automatically.)
- **Do not touch the eval protocol** (5 seeds × 4 episodes × horizon 50) — comparability with the audited run depends on it.
- **`fallback_count > 0` is a failure, not a warning.** The evaluator swallows `ValueError`/`RuntimeError` from `policy.act` into "do nothing" ([evaluator.py:100](../../src/real_ecology_benchmark/evaluator.py#L100)); a broken solver can otherwise look like a healthy conservative policy.

## 8. What the run will and will not show

Expected, from the spot-checks already run:

- The two native baselines are now genuinely distinct methods (PLUS's four-form posterior beats MOOR's single fitted Ricker where the forms disagree: Iberian lynx/allee 9.93 vs 8.60).
- **Spotted turtle** is the one population where all four mechanistic forms agree everywhere — PLUS and MOOR will legitimately coincide there. Not a bug.
- **Egyptian vulture** has *no* action with `r_setpoint > 0`: it is a pure demographic sink where management can only slow the decline. Expect it (and Bottlenose dolphin) to behave unlike the seven recoverables — which is why sinks are reported separately.
- The money plot is return + collapse **by σ and by dynamics family**: the naive Ricker-form solver should degrade visibly on allee/theta/regime cells.
