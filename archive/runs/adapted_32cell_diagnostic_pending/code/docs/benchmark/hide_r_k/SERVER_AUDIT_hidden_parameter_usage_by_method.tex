\section{Purpose and Verdict}

This document is a TeX version of the hidden-parameter usage audit for the
current real-ecology benchmark. It is documentation only: no source code,
configuration, or experiment logic is changed by this report.

The current benchmark is internally consistent with its recent documentation, but
the documentation makes several ecological quantities public that would be hidden
under a stricter POMDP design. The most important distinction is:

\begin{itemize}
  \item \textbf{Private/evaluator-only:} true abundance, hidden structural
  parameters such as \code{r_base}, \code{C}, \code{theta}, latent regime,
  true effective-growth diagnostics, reward diagnostics, and collapse/safety
  diagnostics.
  \item \textbf{Method-facing by current spec:} \code{rho}, \code{kappa},
  \code{K_eff}, \code{next_rho}, \code{next_kappa}, \code{next_K_eff},
  \code{K_ref}, \code{K_base}, \code{K_max}, \code{safety_threshold},
  population identity, family/config identity, and action-table-derived
  \code{delta_r}, \code{delta_K}, and \code{stocking_delta}.
\end{itemize}

Therefore the issue is not primarily a private-sidecar leak. The issue is that
the public benchmark spec itself exposes action-specific growth set-points,
capacity-control state, species-scale carrying-capacity quantities, and
K-derived safety thresholds. General methods consume those mostly as public
features and planning context. Mechanistic and native ecological methods consume
the same public structure as exact transition/reward model inputs, which creates
the mechanistic-planner advantage seen in the motivation experiment.

\section{Method Notes}

\subsection{\code{refplan}}

\code{refplan} fits \code{ContinuousDynamicsEnsemble} with
\code{env_cfg.K_ref} and \code{env_cfg}. The shared ensemble design includes
public-control columns \code{rho_next}, \code{kappa_next/K_ref}, and
\code{K_eff_next/K_ref}; fitting pulls \code{cache.rho} and \code{cache.kappa}.
Planning uses \code{ParticleMPC}, which copies \code{belief.rho} and
\code{belief.kappa} into rollout state and advances public controls. The member
posterior update also calls \code{mean_next} with \code{belief.rho} and
\code{belief.kappa}. See \code{refplan.py:36--100},
\code{dynamics.py:40--120}, and \code{planning.py:69--146}.

\subsection{\code{bamcts}}

\code{bamcts} fits the same control-aware \code{ContinuousDynamicsEnsemble}.
Its tree key buckets \code{rho} and \code{kappa}; simulations pass those controls
to learned dynamics, advance public controls, compute reward/safety from config,
and recurse on the next controls. See \code{bamcts.py:45--145}. A minor
implementation wrinkle is that \code{observe()} calls \code{mean_next} without
\code{rho/kappa}; this is an update inconsistency, not an extra hidden-parameter
exposure.

\subsection{\code{ogsrl}}

\code{ogsrl} consumes public r/K controls in multiple places. The guardian
feature map includes \code{rho}, \code{kappa/K_ref}, and \code{K_eff/K_ref};
policy state features do the same; rollouts pass \code{rho/kappa} into learned
dynamics and advance public controls. Fitting trains both dynamics and the KNN
guardian with belief-cache controls. See \code{ogsrl.py:35--77},
\code{164--245}, and \code{297--435}.

\subsection{\code{moor_native}}

\code{moor_native} reads public \code{dataset.kappa}, searches a scalar
\code{K_hat}, and targets next observations normalized by \code{K_ref}. It then
builds a native solver with \code{assumed_K_base=K_hat}. The prediction and
solver paths still call \code{resolve_actions}, \code{build_reward}, and
\code{transition_value}, so exact public action growth, capacity increments,
translocation magnitudes, action costs, and safety scale are available. See
\code{moor_native.py:24--55} and \code{native_solver.py:73--255}.

\subsection{\code{plus_native}}

\code{plus_native} does not fit r/K from public transition data. Its \code{fit}
method ignores the dataset and builds one \code{NativeSolver} per candidate
family. It then updates model evidence from action/observation evidence and
acts by posterior-weighted native action values. Each candidate solver uses exact
public action/species/reward structure. See \code{plus_native.py:1--126} and
\code{native_solver.py:35--255}.

\subsection{\code{mopo}}

\code{mopo} fits the same control-aware learned dynamics ensemble as the other
general model-based planners. It computes diagnostics with \code{beliefs.rho}
and \code{beliefs.kappa}, and acts through \code{ParticleMPC}. See
\code{mopo.py:18--60}.

\subsection{\code{delphic}}

\code{delphic} does not fit a mechanistic dynamics model, but it consumes
\code{beliefs.features}, \code{beliefs.next_features}, and public rewards. Since
\code{BeliefState.features} appends public controls when enabled, Delphic gets
an indirect r/K channel. See \code{delphic.py:52--57}, \code{102--120},
\code{182--256}, and \code{types.py:84--118}.

\subsection{Adapted \code{plus}}

Adapted \code{plus} uses a Ricker-style candidate bank. In set-point mode, its
own comment states that per-action growth is known and candidate models span
\code{K_base} to \code{K_max}. Candidate proposals are
\code{MechanisticProposal} objects, so they call \code{resolve_actions} and
precompute exact action lookups. Candidate belief banks preserve
\code{rho/kappa/K_eff}. See \code{plus.py:26--163} and
\code{beliefs.py:324--390}.

\subsection{Adapted \code{moor}}

Adapted \code{moor} fits a single Ricker proposal from public belief means,
actions, and controls. In set-point mode the code treats r as known from
\code{rho}; the fit mainly identifies K. The fitted proposal then plans with
\code{ParticleMPC}. See \code{moor.py:23--115}.

\section{Conclusion}

The audited methods do not appear to train or deploy directly on private sidecar
arrays. The load-bearing exposure is public-by-spec: action-specific growth
set-points, capacity controls, species-scale K quantities, K-derived safety
thresholds, and table-derived action effects are available to methods. Learned
general methods use these as features and rollout context. Mechanistic and native
ecological methods use them as exact model inputs. If the next design requires
r/K/action-table quantities to be hidden, the fix should begin by revising the
public-information contract, not by searching for a private-file read.
